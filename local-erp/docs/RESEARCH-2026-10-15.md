# Pesquisa técnica inicial — 2026-10-15

## Escopo

Pesquisa de stack para ERP desktop Windows local-first, priorizando estabilidade, suporte, baixo custo operacional, produtividade e evolução futura para rede local.

## .NET

Decisão: **.NET 10 LTS**.

Motivos:

- .NET 10 está em suporte ativo e é LTS;
- WPF e EF Core 10 seguem ativos e recebem correções/melhorias;
- .NET 11 ainda está em release candidate na data desta decisão e não deve ser base de produção.

Fontes:

- https://dotnet.microsoft.com/platform/support/policy/dotnet-core
- https://learn.microsoft.com/dotnet/desktop/wpf/whats-new/
- https://learn.microsoft.com/ef/core/what-is-new/

## UI desktop

### WPF — escolhido

Pontos fortes:

- Windows nativo e maduro;
- excelente suporte a data binding, templates, DataGrid, teclado e interfaces densas;
- distribuição menos dependente do Windows App SDK;
- continua sendo parte ativa do .NET 10;
- encaixa melhor em ERP Windows-only do que uma camada multiplataforma.

### WinUI 3 / Windows App SDK

Pontos fortes:

- stack moderna oficial da Microsoft para Windows;
- integração visual moderna e APIs recentes.

Custos observados:

- distribuição unpackaged requer runtime Windows App SDK ou self-contained;
- o Windows App SDK 1.8 continua recebendo diversas correções de runtime e UI em 2026;
- para um ERP orientado a tabelas, teclado e estabilidade, o ganho visual não compensa a complexidade extra neste momento.

Fontes:

- https://learn.microsoft.com/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-1-8
- https://learn.microsoft.com/windows/apps/package-and-deploy/unpackage-winui-app

### Avalonia

Boa opção quando multiplataforma é requisito. Como o produto atual é explicitamente Windows, a abstração adicional não traz benefício suficiente para justificar afastar-se da stack desktop nativa escolhida.

Fonte:

- https://docs.avaloniaui.net/

### .NET MAUI / Blazor Hybrid

MAUI é apropriado quando mobile/macOS também fazem parte do produto. O backend WPF para MAUI está marcado pela Microsoft como experimental; portanto, não é fundamento adequado para este ERP.

Fonte:

- https://learn.microsoft.com/dotnet/maui/developer-tools/platform-backends/windows-wpf?view=net-maui-10.0

### Electron / Tauri

Não escolhidos. O produto não precisa de uma runtime web nem de uma ponte web/native para resolver seu problema principal. Isso adicionaria outra superfície tecnológica sem vantagem clara para um ERP Windows-only.

## Banco de dados

### SQLite — escolhido para instalação de uma máquina

Motivos:

- zero configuração e nenhum serviço de banco separado;
- funciona completamente offline;
- integração oficial com EF Core;
- backup online disponível via `Microsoft.Data.Sqlite`;
- excelente encaixe no primeiro estágio do produto.

Restrições importantes:

- **nunca** abrir o mesmo arquivo SQLite diretamente de vários computadores por compartilhamento de rede;
- EF Core/SQLite possui limitações com schema, migrations e certos tipos como `decimal` e `DateTimeOffset`;
- decisões de armazenamento de valores monetários exigem ADR próprio antes do primeiro módulo financeiro/compras.

Fontes:

- https://www.sqlite.org/whentouse.html
- https://learn.microsoft.com/ef/core/providers/sqlite/limitations
- https://learn.microsoft.com/dotnet/standard/data/sqlite/backup

### PostgreSQL — alvo para modo multiusuário em rede

Na data da pesquisa, PostgreSQL 18 é a versão major corrente suportada. O uso futuro será cliente/servidor, com o banco no servidor e clientes acessando por uma camada controlada (diretamente ou, preferencialmente, por serviço/API quando o produto exigir).

Fonte:

- https://www.postgresql.org/docs/current/

### SQL Server / Express

Alternativa tecnicamente viável, especialmente por manter a família Microsoft, mas não escolhida para a primeira instalação devido ao maior peso operacional de instalar/manter um serviço local quando SQLite atende melhor ao cenário single-PC.

## ORM

Decisão: **Entity Framework Core 10**.

Motivos:

- suporte LTS alinhado ao .NET 10;
- provider oficial SQLite;
- migrations, tracking e transações adequados ao produto;
- permite adicionar provider de PostgreSQL no futuro sem levar SQL para a UI/domínio.

Pacote base verificado: `Microsoft.EntityFrameworkCore.Sqlite 10.0.13`.

Fonte:

- https://www.nuget.org/packages/Microsoft.EntityFrameworkCore.Sqlite

## MVVM

Decisão: **CommunityToolkit.Mvvm 8.4.2**.

É mantido no ecossistema Microsoft/.NET Foundation, é leve e UI-framework agnostic. Evita criar infraestrutura própria de `INotifyPropertyChanged`/commands.

Fontes:

- https://learn.microsoft.com/dotnet/communitytoolkit/mvvm/
- https://www.nuget.org/packages/CommunityToolkit.Mvvm

## Logging

Decisão: **Serilog + File sink**.

Configuração inicial:

- arquivo diário;
- rotação por tamanho;
- retenção de 30 arquivos;
- diretório separado em `%LocalAppData%\LocalErp\Logs`;
- nenhuma senha/token/dado sensível deve ser registrado.

Fontes:

- https://github.com/serilog/serilog-sinks-file
- https://www.nuget.org/packages/Serilog

## Autenticação

Diretriz:

- autenticação local deve ser validada na camada de aplicação;
- senha nunca em texto puro;
- Argon2id é a preferência de segurança conforme OWASP;
- antes da implementação, será feita revisão de pacote .NET Argon2id mantido e sua licença;
- fallback aceitável: `PasswordHasher<TUser>` da Microsoft, sem implementar criptografia própria.

Fontes:

- https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- https://learn.microsoft.com/aspnet/core/security/data-protection/consumer-apis/password-hashing

## Instalação e atualização

Decisão arquitetural inicial: **Velopack**, a ser implementado apenas na fase de distribuição.

Motivos:

- suporte explícito a WPF/.NET;
- integra instalador e atualização;
- suporta setup per-user e MSI/per-machine;
- recomenda publicação self-contained;
- permite controlar check/download/apply da atualização.

MSIX continua como alternativa caso o ambiente empresarial futuro exija Store/Intune/App Installer e package identity.

Fontes:

- https://docs.velopack.io/getting-started/wpf
- https://docs.velopack.io/packaging/installer
- https://learn.microsoft.com/windows/apps/package-and-deploy/

## Backup

Para SQLite, o plano é usar a API de backup do próprio mecanismo via `SqliteConnection.BackupDatabase` em vez de uma cópia de arquivo ingênua enquanto a aplicação está gravando. Todo backup deverá ser validado por abertura/integridade e a restauração será testada automaticamente quando a fase for implementada.

Fontes:

- https://learn.microsoft.com/dotnet/standard/data/sqlite/backup
- https://sqlite.org/backup.html

## Atualização — ciclo CONTINUE 2026-10-15

- .NET 10.0.13 é o patch atual publicado em 13/10/2026; SDK corrente da feature band principal: 10.0.402. O `global.json` foi atualizado para esse baseline.
- A documentação oficial do SQLite classifica shared-cache como obsoleto/desencorajado; WAL atende melhor aos cenários de concorrência local.
- A documentação do Microsoft.Data.Sqlite alerta explicitamente para remover `Cache=Shared` ao usar WAL.
- `EnableWindowsTargeting=true` permite validar o build WPF em Linux/macOS, embora release final deva continuar sendo produzida e testada em Windows.
- O provider SQLite do EF Core mantém limitações de comparação/ordenação para `decimal`; o ADR-0005 define armazenamento monetário exato em inteiro escalado para campos consultáveis.


## Atualização — persistência e migrations

- `Foreign Keys=True` no `Microsoft.Data.Sqlite` envia `PRAGMA foreign_keys = 1` ao abrir cada conexão; `Default Timeout` define o timeout padrão de comandos.
- `dotnet-ef 10.0.13` foi confirmado como a versão estável alinhada ao EF Core 10.0.13 usado pela solução e foi fixado como ferramenta local do repositório.
- a documentação do EF Core recomenda cautela com `MigrateAsync()` em produção e apresenta migration bundles/scripts como opções mais controláveis; por isso o ADR-0006 move a aplicação de schema para o atualizador.
- desde EF Core 9 existe locking de migrations, e o comando `dotnet ef migrations has-pending-model-changes` pode detectar divergência entre modelo e último snapshot; essa verificação entrará na CI após a primeira migration.

Fontes:

- https://learn.microsoft.com/dotnet/standard/data/sqlite/connection-strings
- https://learn.microsoft.com/ef/core/managing-schemas/migrations/applying
- https://learn.microsoft.com/ef/core/cli/dotnet
- https://www.nuget.org/packages/dotnet-ef/10.0.13
